# Payment Date Prediction

A Python pipeline that predicts when open B2B invoices will be paid:
clean and validate the invoice ledger, engineer payment-behavior
features, compare five regression models on a held-out test set, and
export predicted payment dates with aging buckets for the invoices
still awaiting payment.

## The workflow

| Step | What the pipeline does |
|---|---|
| 1. Data inspection | Loads 50,000 rows x 19 columns; reports types, missing values (payment terms, customer name), and 2,308 duplicate rows |
| 2. Data cleaning | Drops redundant/unused columns (`posting_id`, `area_business`, `is_open_item`) and exact duplicates — 47,692 rows remain |
| 3. Standardization | Parses date fields; normalizes USD/CAD amounts (CAD x 0.74 = USD); payment terms to numeric days |
| 4. Dataset preparation | Splits 38,325 labeled rows (clearing date known) from 9,367 unlabeled rows (clearing date to predict) |
| 5. Feature preparation | Date components, categorical encoding, and customer-level average payment delay |
| 6. Model comparison | Linear Regression, Support Vector Regression, Decision Tree, Random Forest, XGBoost — all scored on the same held-out test set |
| 7. Prediction output | Predicted delays, predicted payment dates, and aging buckets for the 9,367 open invoices, exported as CSV |

## Correctness fix vs. the original notebook

The original notebook computed customer-level target averages **before**
splitting the data, so test-row features leaked their own target values
and its evaluation scores were not reliable evidence of predictive
performance. This rebuild fixes that:

- The labeled data is split into train/test **first** (80/20).
- Customer-level average delay and invoice counts are computed from
  the **training split only**; unseen customers fall back to the
  training global mean.
- Every model is scored on the same held-out test set.

A second real-world quirk is handled in the loader: the region code
`"NA"` (North America) is a valid value, not a missing marker — pandas
reads `"NA"` as NaN by default, so the loader switches off the default
NA set and treats only empty strings as missing.

## How to run

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# Regenerate the synthetic sample data (optional — a copy is bundled)
.venv/bin/python scripts/generate_sample_data.py

# Run the full pipeline
.venv/bin/python src/predict.py --data data/invoices.csv --out outputs/
```

## Input format

One row per invoice:

| Column | Meaning |
|---|---|
| `business_code` | Business unit code, e.g. `U001` |
| `cust_number` | Customer identifier |
| `name_customer` | Customer name |
| `clear_date` | Payment clearing date (empty = still open) |
| `business_year` | Fiscal year of the document |
| `doc_id` | Document identifier |
| `posting_date` | Posting date |
| `document_create_date` | Document creation date |
| `due_in_date` | Payment due date |
| `baseline_create_date` | Baseline date for payment terms |
| `cust_payment_terms` | Payment terms, e.g. `N30` |
| `amount_local` | Invoice amount in local currency |
| `invoice_currency` | `USD` or `CAD` |
| `document_type` | Document type, e.g. `RV` |
| `posting_id` | Posting identifier (unused, dropped) |
| `area_business` | Business area (constant, dropped) |
| `is_open_item` | 1 if no clearing date (redundant, dropped) |
| `payment_method` | `ACH`, `Wire`, `Check`, `Card` |
| `region` | `NA`, `EU`, `APAC` |

Lines starting with `#` are ignored, so the synthetic-data banner in
the sample file does not affect parsing.
